Nuclear Option server mods: what the overnight tests showed

Linux dedicated server · Nuclear Option 0.34.1, Steam build 24724541, game build cb745d6c44f1 · BepInEx 5.4.23.3 · No production deployment was performed.

Findings

Watch the simple explanation · Source and installation guide · Plain-language overview

Three optional optimizers reduce specific method costs in benchmarks; a fourth plugin provides diagnostics. Extensive parity tests reproduce the original method results. A whole-server speedup has not been established. The shorter Escalation trials stayed within baseline variation, and the paired hour involved different combat workloads.

  • Method gains are real but small in context. Spatial cut its target method's time by about 28–33% in benchmarks. In a full Escalation hour that method cost roughly 0.031 ms per game frame, which limits the expected loop-time gain in that observed workload.
  • One paired hour is inconclusive. With all three optimizers on, mean loop time was 21.68 ms versus 20.05 ms with all off (8.1% higher), yet the final segment was lower (37.15 vs 38.80 ms). The runs saw different combat workloads.
  • Both long runs aged heavily. An instrumented unoptimized hour shows more physics steps per game frame and higher cost per step late in the mission. The underlying cause is unproven.
  • Vanilla clients are not live-tested. Static inspection found no new network messages, but live joining and rejoining with an unmodded client were not tested in this isolated lab.

Defaults: Spatial on; Wrecks, Navigation and Diagnostics off. A runtime guard requires the exact tested Assembly-CSharp.dll SHA256.

Mission results

Four ten-minute Escalation comparisons, with extra instrumentation off and four startup windows excluded, gave baseline/Spatial loop means of 14.04/14.03 ms and 14.43/14.00 ms. Differences of about 0.1% and 3.0% fall within baseline variation.

Loop time is the game's own total of update, accumulated fixed update and late update per game frame. It is not FPS or wall-clock frame latency and excludes frame-rate pacing.

Late-mission slowdown

A final unoptimized Escalation hour ran with sampled methods and four phase probes. Its 115 steady reports recorded 141,754 game frames and 206,105 physics steps; loop work averaged 20.54 ms per game frame. It is an observation, not an optimizer comparison.

Units matter here. Accumulated fixed time sums all fixed steps within a game frame, so it is per game frame. Phase probes report time per physics step. Multiply cost per step by steps per frame to relate them.

From the first to the final segment, loop time rose from 13.85 to 48.08 ms per game frame and accumulated fixed time from 9.32 to 36.85 ms. Physics steps per game frame tripled, 1.05 to 3.37, while physics cost per step rose from 4.37 to 5.54 ms after peaking at 6.19 ms in windows 85–104; fixed scripts went from 1.85 to 2.87 ms per step.

More steps and dearer steps coincide with the slowdown. That explains part of the fixed-time growth; it does not establish the root cause or a behavior-preserving way to remove that work. No physics or AI cadence was changed.

The paths targeted by the optimizers were small in this unoptimized profile: unit-grid queries cost roughly 0.031 ms per game frame and fully timed road pathfinding about 0.075 ms per game frame over 1,299 calls. These inclusive estimates overlap and carry observer cost, so they cannot be summed.

Validation and client coverage

The baseline is Harmony reverse patches of the actual shipped game methods. Runtime6 passed 1,843,424 assertions. Two runtime10 processes repeated those checks with added edge cases, each passing 2,458,591 assertions, a count that includes a separate empty-only lab experiment. Assertions are checks over many inputs, not independent confidence samples.

Live reload tests took baseline and all-optimizer configurations through three mission transitions across four populated Terminal Control/Escalation phases, with 106,391 and 106,423 live-query/state assertions respectively.

What the parity assertions cover
  • Candidate identity and order, target/state results, road route, status, parent and bitwise float parity.
  • Nested and off-thread fallbacks, exception cleanup, capacity trimming and Unity RNG state.
  • Runtime10 added 1,488 fractional/nonfinite spatial cases and null cell/output exception parity.
  • Current DLLs passed independent loading, all-disabled mode and rejection of an unknown game assembly.
  • Historical terminal-*-06 runs were actually Free Flight (the launcher split the mission argument); later runs verify the mission from logs.

Limits. Wreck parity uses an inactive attached Unit and does not exercise every live depot/navigation callback. Long missions exercise live simulation but are not deterministic equivalence replays.

Clients. Clients install nothing, and static inspection found no new messages or plugin-list requirement, but unmodded client join and rejoin were not live-tested. Tests used isolated offline hosting without human players; Steamworks reported a startup exception, so authentication and client-flown aircraft are outside measured coverage.

Safety. On an unknown game assembly the plugins fail closed and the original methods stay active. Targets already modified by another prefix or transpiler are skipped at startup; third-party patches installed later are not covered. Revalidate after every game update.

  1. Install BepInEx 5 for the Linux server, and in BepInEx/config/BepInEx.cfg set the line below. Without it, the tested build skipped later plugin lifecycle callbacks.
  2. Copy only the DLLs you want into BepInEx/plugins/ and restart.
  3. Enable or disable each plugin in its agent.noperf.*.cfg, then restart again.
  4. To uninstall, stop the server and remove the DLLs.

Other audits

  • Detector raycasts were already batched and network writers already pooled; objective checks and send cadence were too cheap to justify a large patch.
  • Weapons: a 15-minute profile logged over a million trajectory calls. Blast and penetration averaged 0.227 and 0.199 ms inclusive; no large, safe patch was justified.
  • Effects, debris and wreck lifetimes consume RNG or apply forces and callbacks, so skipping them needs further behavioral proof.
  • The unit registry keeps historical references used later by tracking and message code; pruning them is not demonstrated safe.
  • The job manager orders dependent native jobs, pilot inputs and results; moving or skipping those points has not been demonstrated safe.
  • Worker-pool trials (14.20/14.02/14.03/14.36 ms) gave no tuning recommendation.
