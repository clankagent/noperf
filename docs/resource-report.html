Nuclear Option dedicated server · automated multiplayer testing

What a server used with four active pilots

Four scripted test pilots joined a Linux dedicated server over the game’s normal network connection, took off in the stock Escalation mission and flew and fired guns for ten minutes. This page shows what the server used while that happened, and what the test still can’t tell you.

Useful measurements; capacity is still unproven

The newer Ryzen machine completed three four-pilot baseline runs. In their ten-minute flight windows the server averaged 0.76–0.77 CPU cores and peaked at 1.04–1.14 GiB. This describes those runs, not the minimum hardware for an hour-long battle or a larger player count. The test clients competed with the server for the same four vCPUs.

✓Shown with real game processes

  • A Nuclear Option 0.34.1 Linux dedicated server hosted four connected pilots in stock Escalation. Every pilot taxied, took off and climbed for 3 minutes, then flew and fired short gun bursts for 10 minutes. Three independent baseline runs and one matched Spatial run passed all 50 checks each.
  • During those 10 minutes the server process averaged 0.76 of one CPU core and peaked at 1.14 GiB of memory.
  • The physics simulation averaged 60 steps per second. The server’s update loop averaged 55.4 per second.
  • Two-pilot runs also covered rockets, ejecting in the air, taking a replacement aircraft and flying again.

✕Not shown yet

  • How many players a production server can hold. The server and all test clients shared one small virtual machine.
  • Whether the optional NOPerf Spatial plugin helps the whole server. One matched pair finished, with almost identical CPU use. Earlier attempts failed; more repeats are needed.
  • Behaviour with human players or retail Steam clients.
  • Sessions of an hour or more, reconnecting mid-flight, or switching missions with players in the air. Those either failed or haven’t been tested.
  • A completely unmodded server. Every measured baseline also loads the BepInEx mod loader and the test bridge.

What the players actually did

The pilots weren’t people. Each one was a headless test client: a copy of the game’s dedicated-server build running without graphics, joining like an ordinary networked player over UDP. A small scripted controller flew each aircraft by sending control inputs through the game’s own control path. They are not retail Steam clients and not combat AI.

About the “1,000 units” in this mission

During the flight the game’s unit list held between 1,008 and 1,077 entries. That count covers all kinds of mission objects. Only 10 to 12 of them were aircraft at any moment. It does not mean a thousand AI aircraft were flying.

Why the lab can’t establish production capacity

The numbers above describe one test machine, not a recommendation for your server. On this lab the server process alone averaged under one core with four active pilots in this mission. Going further than that would not be honest yet.

The server and the players shared one machine

The lab is a single virtual machine with 4 vCPUs and 8 GiB on an AMD Ryzen 5 PRO 3600 host. The server and all four test clients ran inside it. The clients together used about 2.7 cores, roughly three and a half times what the server used. On a real server, players’ games run on their own computers.

The machine was crowded

During the 10-minute flight the machine was 86% busy. Some task was waiting for a free CPU 57% of the time. In two-pilot runs that wait was about 10% or less, and the server’s update loop held close to 60 per second. With four pilots it fell to 55.4. We can’t yet tell how much of that drop is extra game work and how much is the server queueing behind its own test clients.

Other limits

  • Limited repeats. Three independent four-pilot baselines and one matched Spatial run have passed. The detailed figures here come from the first one. Only one complete baseline/mod pair is available; more are needed.
  • Averages hide spikes. A 0.76-core average can still include short moments where the main thread was the bottleneck.
  • Not stock. The “baseline” loads BepInEx and the NOTestPilot bridge. A loader-free stock server is a separate test.
  • Scripted pilots. A simple circuit controller isn’t human flying or combat. Deliberate hits on targets weren’t verified.
  • Different hardware gives different numbers. These results apply to this guest only.

Mod comparison and failures

No whole-server benefit from the optional performance plugin has been shown.

Where the profiler points next

In the two-client mission profile, the native physics phase averaged about 2.0 ms per simulation step. Script phases averaged about 1.1 ms for simulation, 1.2 ms for updates and 0.5 ms for late updates. Job scheduling was a larger measured method than the spatial lookup helper. Three further, shorter profiling runs completed. They separated ground-vehicle input collection from aero input and job waits, giving the next optimization attempts a measured starting point.

These are measurements with extra instrumentation, after discarding the first four diagnostic windows. The window includes takeoff and flight, and the run later failed. Method timings can overlap and include waiting; they are not pieces of a CPU pie, a capacity estimate or a measured mod gain.

Two new performance ideas checked

Reusing an aircraft velocity read: rejected. It was faster in a synthetic case where adjacent parts shared a body. The real mission recorded 1.50 million reads and no adjacent reuse. Keeping that cache would add work without helping this workload.

Visiting only due ground vehicles: experimental source available. The game already spreads some ground input work over twelve ticks. Visiting just the due indices kept the original order in 6,360 native checks. The isolated scan became about ten times cheaper, saving roughly two microseconds per loop; actual vehicle callbacks and physics still do their original work.

Two shorter, two-pilot baseline/mod pairs passed all 30 checks per run through three minutes of takeoff and three minutes of flight with guns. The mod’s patch was confirmed active. Flight CPU was lower in both mod runs, but the difference varied and mission workloads diverged. This is too little evidence to call a useful whole-server gain or memory reduction.

Failures we’re keeping on record

Failed runs stay in the record. They are part of the evidence.

  • A later mod run failed during mission loading. A candidate run and a later baseline without the performance plugin both failed while the fourth client loaded Escalation, before flight began. Another baseline failed during a later attempt to join. The loading problem occurs in both variants; its cause remains unresolved. A read-only trace caught a destroyed aircraft left in the client’s mission lookup just before the original error. We have identified the stale entry, but not the full sequence that leaves it there. A delayed second-client join passed a focused test; that does not resolve the intermittent fault.
  • Earlier four-pilot version ran out of ammunition. One-second bursts every 20 seconds emptied every gun, so the final check failed. The script now uses half-second bursts. That’s the version that passed.
  • Reconnecting while flying fails. When a client leaves mid-flight, the game hits an error while it cleans up the mission on that client. This happened in both attempts, including with the normal Quit path. Short idle join, leave and rejoin passed.
  • Changing missions with players in the air fails. Rotating from Escalation to Terminal Control failed during server cleanup. The return rotation was never reached. An older, separate cleanup failure is also on record.
  • Short flights can still end in a breakup. One two-pilot repeat lost an aircraft to impact damage at 2 min 52 s. A later profiling run also lost height just before the end of its ten-minute flight window. Its trace captured joint breaks at about 935 metres, followed by collisions between parts of the same aircraft. The initiating cause remains unresolved; the profiling run is a failure.
  • A stop-on-request test behaved as intended. A run stopped deliberately at about 10 seconds kept its partial data, archived its logs and stopped its own game processes. It’s recorded as cancelled, not as a pass.
  • An older long run has an unknown result. A three-sortie run on the previous lab was interrupted before its result could be collected. It isn’t counted.
Technical detail for these failures
  • Occupied disconnect: client-side exceptions in RadarWarning.Update and, in another run, ThreatItem.AnimateItem / ThreatList.Update during mission unloading. Retail reproduction unverified.
  • Occupied rotation: server Turret.ChooseTarget / Turret_OnTargetDisabled during unit destruction; clients also logged StatusDisplay cleanup exceptions. The older failure was in ship particle cleanup on Terminal Control. Game logic was not modified to hide either.
  • Three-sortie gun flight: missile blast or fragment damage reached a pilot, then own-part collisions and descent. The attacker is unknown.
  • The initiating cause in the Spatial run and the two-pilot breakup is unresolved. Read-only joint and body diagnostics were emitted.

Next tests

The repeatable flight and replacement foundation is working. These are the remaining gaps before recommending a production setup.

  1. Repeat the pairs so differences can be compared with ordinary run-to-run variation.
  2. Longer sessions, tracking slow frames and whether the mission slows down as it ages.
  3. Larger missions with more active units, with simulation settings left unchanged.
  4. A fully stock server without BepInEx, kept separate from the instrumented baseline.
  5. Separating client load from the server. This is needed before any capacity statement is possible.
  6. Reconnect and mission-rotation failures, plus the unexplained aircraft breakups.

Human players, retail Steam clients and Steam authentication remain untested.
